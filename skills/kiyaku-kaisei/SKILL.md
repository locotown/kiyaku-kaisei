# 管理規約 改正対応チェック

## 前提
- 対象：単棟型のマンション。比べる相手は「マンション標準管理規約（単棟型）令和7年10月17日改正」
- 区分所有法は、令和7年法律第47号による改正後（2026年4月1日施行）の条文を使う
- 2026年4月1日以降に招集する総会には改正法が適用される。施行の際に効力を持つ規約の定めのうち、改正法に**抵触するものは施行日から効力を失う**（令和7年改正法 附則第2条第3項）
- 出力は「総会提案の下書き」であり、法的助言ではない
- **日付に注意**：依頼文の「基準日」を必ず確認する。改正前の規約の定足数・決議要件で決議できるのは、施行日前（2026年3月31日まで）に招集手続きを始めた総会だけ（附則第2条第2項、国交省「手続の留意点」）。基準日が施行日以降なら、規約の改正も改正法の要件（組合員総数・議決権総数の各過半数の出席、出席者の各4分の3以上）で決議すると案内する。過ぎた期限を勧めない

## 手順
1. `list_articles` で現行規約の全体像をつかむ
2. `reference/topics.md` の論点表を読み、論点ごとに次を行う
   - 現行規約で対応する条を探す。条番号は標準管理規約と同じとは限らないので、見出しと内容で探す
   - `get_articles` で現行規約の本文を、`get_standard_articles` で標準管理規約の本文を、`get_law_articles` で区分所有法の条文を取得し、照らし合わせる
   - 改正後の標準管理規約・改正法と食い違う場合は指摘にする。すでに対応済みなら指摘しない
3. 論点表にない差分（電磁的方法の整理など）は、標準管理規約と比べて意味のある違いがあり、根拠を示せるものだけを「参考」として指摘する
4. 指摘は `record_findings` で記録する。受け付けられなかった指摘は、返ってきた理由に従って直して送り直す
5. 最後に、件数と、担当者が判断すべき点を短くまとめる

## 細則の点検（細則がある場合）
規約集に細則（使用細則・駐車場使用細則・集会室使用細則など）が含まれる場合は、`list_rules` で一覧を確認し、`get_rule_articles` で本文を読んで、次を点検する。指摘の `document` には細則の題名を入れる。
1. **改正法との食い違い**：細則に、改正区分所有法に抵触する定めがないか（例：総会の招集期間を1週間より短くできる定め、総会の決議要件を独自に定めている箇所）
2. **規約との食い違い**：細則が、規約にない条・削った条・番号の違う条を参照していないか。規約より細則が優先するような書き方になっていないか。細則の改廃の手続き（総会の決議など）が規約と合っているか
3. **規約で定めるべき事項**：区分所有法上、規約で定めなければ効力がない事項（専用使用権の設定、管理費等の負担割合、決議要件など）を細則だけで定めていないか。あれば規約に移す改定を提案する（`document` は「規約」）
4. **細則で対応できる指摘の受け皿**：規約の点検で `where` を「細則で対応可」とした指摘は、該当する細則があればその細則を `document` にする。該当する細則がなければ `document` を「規約」のままにし、`proposal` に「新しい細則を設ける」と書く
- 細則の変更は総会の普通決議で足りる（標準管理規約第48条第一号、第47条第2項）。規約の変更（特別決議）と分けて扱う
- 細則独自の運用ルール（駐車場の使用料、集会室の使用時間など）は、改正法と関係がなければ指摘しない

## 指摘の書き方
- **根拠を示せない指摘は出さない**。区分所有法の条文（例：「第31条第1項」）か、標準管理規約の条番号（例：「第47条第3項」）を必ず付ける
- `current_excerpt` には、`get_articles` で取得した本文から一字一句そのまま引用する。現行規約に規定そのものがない場合は、`article` を「規定なし」、`current_excerpt` を空にする
- `issue` は、専門家でない理事会の担当者が読んで分かる言葉で書く。法律用語を使うときは短く言い換える
- `issue` と `proposal` で条番号を書くときは、**どの規約の条か**（今の規約／標準管理規約／区分所有法）と**何を定めた条か**を必ず添える。条番号だけを突然出さない
  - 悪い例：「第67条の4・第67条の5を新設し、議決権行使（第46条）も定める」
  - 良い例：「標準管理規約にならい、管理命令を理事長が裁判所に求める手続き（標準管理規約 第67条の4・第67条の5）を新しい条として設ける。あわせて、裁判所が選んだ管理人が総会で議決権を使えることを、今の規約の議決権の条（第46条）に加える」
- `proposal` は、何をどう変えるかを先に書き、条番号は括弧で補う
- 区分
  - **必須**：論点表で「必須」のもの。改正法に抵触する、または国交省が必ず盛り込むよう求めているもの
  - **推奨**：論点表で「推奨」「要確認」のもの。「要確認」は、法に抵触するかを一次資料で確認できていない論点
  - **参考**：論点表にない、標準管理規約との意味のある違い
- **規約か細則か**（`where`）：規約の変更は特別決議（区分所有法第31条第1項、標準管理規約第47条第3項第一号）。使用細則などの細則の変更は普通決議で足りる（標準管理規約第48条第一号、第47条第2項。根拠は第18条・第70条）。総会・理事会の運営、会計処理、届出事項など、標準管理規約が細則に委ねている事項は「細則で対応可」とする
- **選択式の規定**：標準管理規約に（ア）（イ）などの選択肢がある場合（例：電磁的方法が利用可能か）は、勝手に選ばず `choice_needed` を true にし、`choice_note` に選択肢と判断のポイントを書く
- 1つの条に複数の論点がある場合（第47条など）は、論点ごとに別の指摘にする

## してはいけないこと
- 根拠のない推測で指摘を作る
- 現行規約にない文言を引用する
- 法的な結論を断定する（「無効です」ではなく「改正法に抵触し、効力を失うおそれがあります」）

## 改定案の書き方（改定案を作るとき）
- 各改定の `document` に、規約本体なら「規約」、細則ならその題名を入れる。規約の改定（特別決議）と細則の改定（普通決議）は、総会で別の議案になる
- 細則の条番号・項目番号は、その細則の中の番号を使う。項目形式の細則（「1. 管理員」）なら `article` は「2.」のように書き、`text` も「2.　…」で始める
- 方式は「現行規約ベース（一部改正）」。指摘に対応する部分だけを変え、それ以外の文言は変えない
- 条番号は振り直さない。新しい条は枝番で追加する（例：第24条の2、第67条の3）。標準管理規約に同じ枝番があればそれに合わせる
- 文言は、改正後の標準管理規約を手本にしつつ、現行規約の言い回し（「組合員」「理事長」「理事会」など）と、項・号の書式を引き継ぐ
  - 条：「第47条　…」で始める。第2項以降は「2　…」、号は「一　…」。各項・各号は改行で区切る
- 1つの条に複数の指摘がある場合は、1つの改定にまとめる
- 他の条を参照する箇所（「第○条」「前条」）は、改定後の規約で正しい条を指すようにする
- 組合が決めるべき事項（電磁的方法の利用の有無、防火管理者の要否など）は勝手に決めない。本文の該当箇所に〔選択〕を付け、`choices` に選択肢と判断のポイントを書く
- `reason` は、専門家でない担当者に向けて、なぜ変えるのかを平易に書く（例：「改正法で、出席者の4分の3で決められるようになりました。今のままでは法律とずれるため…」）
- 書き終えたら `check_draft` で検査し、エラーがなくなってから `/mnt/session/outputs/kaitei.json` に保存する
- `check_draft` の「注意」も必ず読む。採点役がよく指摘する点を先に知らせている
  - 新設の枝番の欠番（例：第69条の2がないのに第69条の3を設ける）：番号を詰めるか、標準管理規約の番号に合わせた理由を notes に書く
  - 改定後の条文が参照する条が、改定後の規約にない：参照先の条番号を直す
- 枝番を付けるときは、同じ条の枝番を「の2」から順に使う（標準管理規約の番号に合わせる場合を除く）
- `notes`（申し送り）は、次の見出しで、担当者が次に何をすればよいかが分かるように書く。該当がない見出しは省く
  1. 【決議の進め方】この規約改正を総会でどの要件で決議するか（基準日と施行日の関係）
  2. 【優先して提案する改定】必須の改定と、その理由（改正法に抵触して効力を失うおそれ、など）
  3. 【組合が選ぶ点】〔選択〕を付けた箇所の選択肢と、決めるために確認すること
  4. 【条・項の番号が変わる箇所】項や号の番号が変わる条（細則・議事録・掲示物などが参照していれば直す必要がある）
  5. 【あわせて検討するとよい点】指摘の対象外だが、改定に伴って見直すとよい条
  6. 【使った資料】標準管理規約・区分所有法の版
- お断りは「総会提案の下書きであり、法的助言ではない」とだけ書く。改正区分所有法に抵触しない範囲では、内容は各管理組合が自由に決められる。専門家への確認を一律に勧めない
