# 仕様（SPEC）

11/2 の仕様インタビューで決めた内容。MVP を作りながら見直す。
本ツールの出力はすべて「総会提案の下書き」であり、法的助言ではない。

## 1. 使う場面

### 使う人と体制
- 主に使う人：規約見直しの担当者（専門家ではない）
  - 理事会の下に見直し委員会を置く組合と、理事会の担当者・理事が直接行う組合の両方を想定する
- 受け取る人：理事会、区分所有者（住民）

### 使う場面
- A. 担当者が**1人で準備**し、結果を委員会・理事会に持っていく
- B. 委員会・理事会の**会議中に画面を共有**し、みんなで見ながら検討する

### 規約改定の4ステップ（ツールが支える流れ）
| ステップ | 主な相手 | ツールが出すもの |
| --- | --- | --- |
| 1. 素案の作成・相談 | 委員会 | 指摘一覧、改定案、論点メモ |
| 2. 改定案の提出・合意 | 理事会 | 改定案、新旧対照表、決議要件の判定 |
| 3. 住民説明会（複数回のことも） | 区分所有者 | 平易な変更理由の説明、想定Q&A |
| 4. 総会での決議 | 区分所有者 | 議案書の文面、新旧対照表 |

MVP はステップ1〜2の中心部分と、ステップ3の説明文を対象にする（「4. 最初に作る範囲」を参照）。

### 改定の方法：2つのパターン
| | パターン1：現行規約ベース（一部改正） | パターン2：標準管理規約ベース（全部改正） |
| --- | --- | --- |
| 進め方 | 現行規約をできるだけ崩さず、必須の箇所と選んだ箇所を直す | 最新の標準管理規約を自分のマンション用に調整し、現行規約と突き合わせて固有の規定を書き戻す |
| 長所 | 変更量が少なく、説明と合意がしやすい | 網羅的で、今後の改正にも追従しやすい |
| 主なリスク | 必須箇所の見落とし、旧版とのずれが残る | 固有の規定の取りこぼし、説明の負担が大きい |

- **MVP はパターン1**を出力する
- **最終目標はパターン2**（作り手のマンションはこちらを想定している）
- どちらのパターンでも中心の処理は同じ「**条文の突き合わせ（対応表）**」。MVP の対応表はパターン2でもそのまま使えるように設計する
- 突き合わせの結果（変更が必要な条の数・割合）を、どちらのパターンを選ぶかの判断材料として示す

## 2. 入力

| 入力 | MVP | 次の段階 |
| --- | --- | --- |
| 現行規約 | テキストを取り出せる形式（Google ドキュメントの書き出し、Word、テキストPDF、テキスト） | 紙のスキャン・写真（OCR） |
| 使用細則などの関連規程 | 読み込み、規約との矛盾を検出する | 細則の改定案も出す |
| マンションの基本情報 | 質問形式で入力する（型、戸数、役員数、電磁的方法の利用状況など） | — |
| 過去の総会議事録・検討メモ | — | 経緯の把握に使う |

- **最初に型を確認する**：単棟型・団地型・複合用途型で、比べる標準管理規約が変わる。MVP は**単棟型のみ**に対応する
- **反映済みの改正を確認する**：現行規約は、本則に後から改正が積み重なっていることが多い。どの改正まで反映した版を正とするかを確認する
- **元にした版を推定する**：現行規約が、標準管理規約のどの版（平成28年・29年、令和3年・6年など）を元にしているかを推定する

### 規約集（規約本体＋細則＋改正履歴など）の扱い（11/2 追加）
- 1つのファイルに規約本体・細則・別表・改正履歴・作業メモが入っている「規約集」を受け付け、文書ごとに分ける（core/collection.py）。分け方は画面に表示し、担当者が確認する
- 細則は条形式（第1条…）と項目形式（1. 管理員…）の両方に対応する
- ページ参照（「規約集 p11」）、◆★※の注記、「出典 = …」のような作業メモは本文から外し、文書ごとに別に保持する
- 改正を反映済みの「現行の本文」を正とする。改正履歴は点検の対象外（最後に改正した時期などの参考情報）
- 点検はまず規約本体。細則の点検と、細則の改定案（普通決議）を規約の改定案（特別決議）と分けて出すのは次の段階

## 3. 出力

### MVP の出力
1. **指摘一覧**
   - 指摘ごとに、根拠（区分所有法の条文、標準管理規約の条番号）、区分（必須・推奨・参考）、「規約で対応／細則で対応可」の判定を付ける
2. **改定案**（パターン1）
3. **新旧対照表**
4. **住民向けの変更理由の説明**（平易な言葉で）
5. **判断の記録**
   - 指摘ごとの採用・不採用・修正と、その理由をツール上に保存する
   - 次の作業では、AI がこの記録をふまえて進める
   - Google ドキュメントなどへの書き出しは結果の出力先にとどめ、正本は記録側に置く

出力の冒頭には「総会提案の下書きであり、法的助言ではない」と明記する。

### 総会後の出力（11/3 追加）
- **総会の結果の記録**：議案（規約本体＝特別決議、細則ごと＝普通決議）ごとに可決・修正して可決・否決、総会の日、施行日
- **最新の規約・細則の全文**（Word）：今の規約に、可決した改定（理事会で見送ったものを除く。総会で修正した文があれば差し替え）を機械的に重ねる。AI は使わない
  - 改正は差し替え、新設は条番号の位置に、削除は「第○条　削除」、附則に今回の施行日を足す
  - 〔選択〕が残っている改定は作らない
  - 書式（字下げ・表・別表）と条番号の書き方は引き継がない。体裁は元の規約集に合わせて整え、議事録と照らし合わせる
- **規約集の改正履歴に足す一行**

### 次の段階の出力（候補）
- パターン2（全部改正）の改定案
- 総会の議案書の文面
- 決議要件の判定の詳細（規約変更＝特別決議、細則変更＝普通決議 など）
- 理事会に上げるときの論点メモ
- 住民からの想定質問と回答（Q&A）
- **スケジュール（工程表）**：総会の日から逆算した期限の一覧（招集通知、説明会、理事会など）

### 規約と細則の切り分け
次の事実をもとに、指摘ごとに「規約で対応／細則で対応可」を判定して示す。

- 規約の変更は特別決議（改正区分所有法 第31条第1項、標準管理規約〔単棟型〕第47条第3項第一号）
- 使用細則などの変更は普通決議で足りる（標準管理規約 第48条第一号、第47条第2項）。細則の根拠は第18条（使用細則）と第70条（細則）

### スケジュールの前提（一次資料で確認済み）
2026年4月1日以降に招集手続きを始める総会について（国交省「手続の留意点」パターン2）

- 現行規約の定足数・決議要件のうち、改正法に抵触する部分は無効になる
- 規約改正の決議は改正法の要件で行う
  - 定足数：組合員総数と議決権総数の各過半数
  - 決議要件：出席組合員とその議決権の各4分の3以上
  - 根拠：改正法 第31条第1項
- 招集通知を出してから総会までの期間は、1週間より短くできない（改正法 第35条第1項）

## 4. 最初に作る範囲（MVP）

機能の開発は 11/7 に止める。

- 型：**単棟型のみ**
- 入力：テキストを取り出せる規約と細則、基本情報（質問形式）
- 中心の処理：現行規約と令和7年改正の標準管理規約（単棟型）の**条文の突き合わせ（対応表）**
- 出力：パターン1の指摘一覧 → 改定案と新旧対照表 → 住民向けの説明
- 記録：指摘ごとの採用・不採用・修正と理由
- 利用形態：**作り手1人で使う**（共有・ログインはしない）
- 評価：「7. 評価方法」の指標を evals/ で測る

## 5. 作らないもの

1. 法的な判断の代行（出力は「総会提案の下書き」であり、法的助言ではない）
2. 総会の運営（議決権の集計、電子投票、委任状の管理）
3. 住民への配信（メール送信や掲示の自動化）
4. Notion / Google ドライブとの連携機能
   - これらは作り手の資料置き場として**開発に使うだけ**で、ツールには組み込まない
   - そこにある非公開資料は CLAUDE.local.md で指定した場所で扱い、コミットしない
5. ログイン、共有、複数組合での利用（マルチテナント）
6. 実在の規約・住民名・部屋番号をリポジトリやデモに含めること
   - デモは公開サンプル（旧版の標準管理規約など）で行う
7. Streamlit の利用

## 6. 必須の改正と推奨の改正の扱い

| 区分 | 意味 | 根拠の示し方 | 改定案への反映 |
| --- | --- | --- | --- |
| **必須** | 改正法に抵触し、そのままでは無効になる、または決議を誤るおそれがある | 区分所有法の条文と、標準管理規約の条番号 | **自動で入れる** |
| **推奨** | 法的には任意だが、令和7年改正の標準管理規約で追加・変更された | 標準管理規約の条番号と、そのコメント | 担当者が選んだものだけ入れる |
| **参考** | 過去の改正（平成28年〜令和6年）の取り込み漏れ、条番号のずれ、古い表記 | 該当する版の新旧対照表 | 担当者が選んだものだけ入れる |

- 必須の例：規約変更などの特別決議の定足数が「議決権総数の半数以上」のままになっている
  - 改正法では「組合員総数と議決権総数の各過半数」になり、半数ちょうどは含まれない
  - 根拠：改正法 第31条第1項、国交省「手続の留意点」※1
- 根拠を示せない指摘は出さない
- **選択式の規定**（例：電磁的方法が「（ア）利用可能ではない場合／（イ）利用可能な場合」）は、ツールが選択肢と判断のポイントを示し、**担当者が選ぶ**。ツールが勝手に決めない
- 論点の一覧は docs/DOMAIN.md（11/2 に一次資料で確定）。区分は国交省「改正の概要」の◎（必須）・○（望ましい）に合わせる

## 7. 評価方法

### 正解データ（公開資料だけで作る）
- 国交省「令和7年改正 改正箇所見え消し（単棟型、Word）」から、**改正前の本文**と**改正箇所**を取り出す
  - 見え消しは変更履歴ではなく書式で表されている（赤の下線が追加、赤の二重取消線が削除）。この規則で改正前・改正後の本文を段落単位で取り出せることを 11/2 に確認した（952段落中184段落が変更）
  - 条の移動（例：第64条の2 → 第31条の2）や、選択式の規定（（ア）（イ））の両案が含まれる点に注意する（docs/DOMAIN.md を参照）
- 改正前の本文をツールに入力し、改正箇所を正解として突き合わせる
- 現実の規約に近づけるため、条番号のずれや言い回しの違いを加えた**加工版**も作る
- 使う公開資料は data/public/ に置き、出典を data/public/SOURCES.md に記録する

### 指標と目標
| 指標 | 内容 | 目標 |
| --- | --- | --- |
| 必須の検出率（再現率） | 必須の箇所をどれだけ漏らさず見つけたか | **100%**（最重視） |
| 指摘の正確さ（適合率） | 出した指摘のうち、正しかったものの割合 | 80%以上 |
| 根拠の正しさ | 指摘に付けた条文番号が正しいか | 95%以上 |
| 区分の一致 | 必須・推奨・参考の分類が合っているか | 計測して記録する |
| 住民向け説明の読みやすさ | 専門用語の言い換え、文の長さなど | 担当者が5段階で評価する |

### 実際の規約での検証
- 非公開の場所（CLAUDE.local.md で指定）でだけ実行する
- リポジトリと発表に出すのは**数字だけ**とする（例：「必須12件中12件を検出」）。規約の文面・物件名は出さない
