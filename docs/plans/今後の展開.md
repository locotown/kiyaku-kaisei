# 今後の展開（ハッカソン後）

11/5 作者の方針：ハッカソンでは「管理組合が自分の API キーで使う形」（B）で提出し、「サービスとして提供する形」（C）を今後の展開として計画に入れる。実用性を示すため。
数字のうち出典がないものは「要確認」と書き、提出文に使う前に確かめる。

## 公開の3つの形（11/5 の整理）

| 形 | 費用を払う人 | いまの位置づけ |
| --- | --- | --- |
| A. 作者のサーバーと API キーで動かす | 作者 | とらない（全利用者の AI の費用が作者の負担になる） |
| B. 管理組合が自分の API キーを入れる | 各管理組合 | **ハッカソンで提出する形**。初めてのキーで AI の設定を自動で登録する（agents/registry.py） |
| C. サービスとして提供し、利用料をもらう | 各管理組合（利用料） | **今後の展開**（このファイル） |

## なぜ C が要るか
- B は、管理組合の担当者が Claude Console でアカウントと API キーを作る必要がある。作者は実際にこの手順を踏んだが、専門家ではない担当者には最初の壁になる
- 規約の見直しは数年〜十数年に一度で、組合にとって API の契約を続ける理由が薄い。「1回の見直しに、決まった料金を払う」ほうが分かりやすい
- 改正区分所有法の施行（2026年4月1日）の前後に需要が集中する。施行後も、規約を合わせていない組合は対応を迫られる

## 段階

### 段階1：試験提供（ハッカソン後〜施行の前後）
- 作者の管理組合（規約見直し委員会）で、委員会・理事会・総会まで通して使い、記録を残す（実在の名前は公開しない）
- 近隣や知人の管理組合に、B の形で使ってもらう。導入（API キーの作り方、Mac・Windows での起動）を作者が手伝う
- 開発中に作った「確認ボード」の進め方で、使う人の気づきを集め、直して自動テストに変える
- 1組合が見直しを一通り終えるまでの、実際の AI の費用と時間を記録する（料金設計の根拠にする）

### 段階2：サービスとして提供（C）
- 作る必要があるもの
  - 管理組合ごとのアカウントとログイン（委員・理事の複数人で使う。いまは1人で使う前提）
  - 組合ごとのデータの分離と、規約・判断の記録の保存（暗号化、削除の手順）
  - インターネットに置くサーバー（いまは手元の PC か Codespace）
  - 支払い（1回の見直しごとの料金、または期間の料金）と、使いすぎを止める上限
  - 問い合わせの窓口
- 料金の考え方（案）：AI の費用（一通しで約 $2〜10。作り直しを含めると増える）＋サーバーと運用の費用＋サポート。専門家に頼む費用（要確認：出典のある数字で比べる）より十分に安く設定する
- 法律の面で気をつけること：出力は「総会提案の下書き」で法的助言ではない、という今の線を守る。必要な組合には、マンション管理士・弁護士の確認を受けられる窓口を紹介する（連携の形は要検討）

### 段階3：広げる
- 複合用途型・団地型の標準管理規約に対応する（いまは単棟型のみ）
- 総会で決まったあとの規約集の版の管理（次の見直しで、最新の規約から始められる）
- 次の法改正・標準管理規約の改正に追従する（スキルと論点表を更新し、評価データで確かめる）
- 管理会社が複数の組合の見直しを手伝う使い方（組合ごとの同意とデータの分離が前提）

## 費用を下げる工夫（C の料金に効く）
docs/plans/コスト.md の「費用を下げる案」を、評価（evals/）で精度が下がらないことを確かめながら入れる。
- 標準どおりの条は、国の改正文を下書きにする（実績：改定案の費用 $3.84 → $2.64）
- 毎回同じ条文・スキル・確認基準のキャッシュ
- 軽い処理に小さいモデルを使う
- 急がない処理をまとめて安く流す
